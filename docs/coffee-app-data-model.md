# コーヒー情報収集アプリ データモデル設計(たたき台)

これまでの調査(産地マスタ・精選方法・国別グレード・焙煎度・特定銘柄)を踏まえたテーブル設計。ER図は`coffee-app-er-diagram.mermaid`を参照。

---

## 1. 設計方針

- **「店舗の商品名(生の文字列)」を分解し、複数のマスタに正規化する**という基本方針
- 産地・精選方法・グレード・焙煎度・特定銘柄は**すべて独立した軸**として持たせる(これまでの調査で確認した通り、同じ「マンデリン」でも焙煎度や精選方法は店舗ごとに異なるため)
- **正規化しきれない情報は無理に分類しない**。`raw_name`(商品名原文)を必ず保持し、パースできなかった部分は`PARSE_LOG`に残して後から人力でマスタを拡充する運用を前提にする

---

## 2. 主要テーブル

### SHOP(店舗)
店舗の基本情報とスクレイピング管理用の情報を持つ。**住所・営業時間は`SHOP_LOCATION`に分離**している(理由は次項)。

| カラム | 説明 |
|---|---|
| platform | Ocnk/独自EC/静的HTML等。スクレイパーのロジック選択に使う |
| shop_type | `online_only`(オンライン専業)/`single_location`(実店舗1件)/`multi_location`(実店舗複数)。フロントエンドの表示分岐に使う |
| robots_txt_status | 収集可否の確認結果を記録し、法務的な根拠を残す |
| last_scraped_at | 定期実行の管理用 |

### SHOP_LOCATION(実店舗)

**新設の理由**: PHILOCOFFEAのように、オンラインストアと複数の実店舗(シャポー船橋店・201・表参道店等)を持つ店舗が実在することが判明した。当初`SHOP`テーブルに直接`address`を1つだけ持たせる設計だったが、これでは複数実店舗に対応できないため、`SHOP`から1対多で参照する独立テーブルに分離した。

| カラム | 説明 |
|---|---|
| label | 実店舗名(例:「シャポー船橋店」「201」「表参道店」)。オンライン専業店舗の場合はこのテーブル自体にレコードを持たない |
| address / prefecture | 実店舗ごとの住所。都道府県は`address`から抽出する派生値 |
| hours / tel | 実店舗ごとに異なりうる営業時間・電話番号 |
| is_headquarters | 本社・焙煎所等、消費者の来店・購入対象ではない拠点を店舗一覧の表示から除外するためのフラグ。PHILOCOFFEAの調査では、店舗ページに掲載されていても「店舗ではなく本社機能」と明記されている拠点があったため、このフラグで区別する |
| mapQuery | フロントエンドの「Googleマップで開く」リンク生成に使う検索クエリ(店舗名+住所) |

**運用イメージ**: `SHOP.shop_type`が`multi_location`の場合、店舗詳細画面は単一の住所ではなく`SHOP_LOCATION`の一覧(各実店舗ごとにGoogleマップリンク付き)を表示する。`online_only`の場合は`SHOP_LOCATION`にレコードを持たせず、オンラインストアのURLのみを案内する。

### PRODUCT(商品)
中心となるテーブル。店舗の1商品=1レコード。

| カラム | 説明 |
|---|---|
| raw_name | 商品名の原文。必須。パース元として常に保持 |
| category | ブレンド/ストレート/**フレーバー**の一次分類。フレーバーコーヒー(焙煎時・焙煎後に人工的な香り付けをしたコーヒー)は、産地・精選方法の個性を扱う本アプリの趣旨と完全に異なる商品カテゴリのため、他のどの判定よりも優先して検出・分離する |
| is_flavored / flavor_name | フレーバーコーヒー判定フラグと、判明したフレーバー名(ココナッツ/アーモンド等)。`is_flavored=true`の場合、産地・精選方法・グレード等の解析は一切行わない(ベース豆の産地表記があっても商品の主眼は香り付けであるため) |
| origin_region_id | ストレートの場合のみ設定。ブレンドはnull |
| origin_source | 産地をどの根拠で判定したかを記録(`brand`=特定銘柄逆引き / `country_name`=国名直接表記 / `region_name`=地域名逆引き / `category_hint`=店舗のカテゴリ・タグ情報による補完)。判定根拠の透明性を残し、精度検証や再パース時の優先順位付けに使う |
| category_hint | 店舗のカテゴリ・タグ情報の原文(例: MiLL Coffeeの「原産国」フィルタ値)。商品名だけで産地判定できない場合のフォールバック情報として保持 |
| designated_brand_id | 特定銘柄14種のいずれかに該当する場合のみ設定 |
| country_grade_id | 「G1」「AA」等の表記。国とセットのレコードを参照するため、国をまたいだ意味の混同を防げる |
| roast_level_id | 焙煎度。**注意: 店舗によっては商品の固定属性ではなく「注文時に選ぶオプション」の場合がある**(例: Denim bisは生豆から7段階の焙煎度を毎注文時に選択する方式で、単一原産地の商品名には焙煎度が含まれない)。固定属性として持つ店舗と、オプションとして持つ店舗の両方に対応できるよう、`PRODUCT`に直接持たせるほか、店舗ごとの販売形態を`SHOP.roast_selection_type`(固定/注文時選択)で分岐する設計を検討 |
| producer_lot_id | 生産者・農園・生産地・標高・品種が判明した場合のみ設定。`PRODUCER_LOT`テーブルを参照(詳細は後述) |
| roast_hint | 店舗が「推奨焙煎度」として参考表示している値(例: MiLL Coffeeの「推奨焙煎度＝ミディアム、ミディアムハイ」)。`roast_level_id`(実際に選択・固定された焙煎度)とは別物として区別する |
| unit_note | 販売単位の原文(例:「230ｇ焙煎」)。重量の単純な数値化が難しい表記のため原文も保持 |
| price_note | 価格が店舗サイトに一切掲載されていない場合の案内文(例: 豆コネクトの「価格は店舗にお問い合わせください」)。量り売り・都度相談等、価格を一意に確定できない販売形態の店舗でのみ設定し、それ以外はnull |
| out_of_stock | 在庫なし表示の商品を除外・区別するためのフラグ |
| decaf_process | カフェイン除去方法の原文(例:「マウンテンウォーター製法」)。デカフェ商品にのみ発生する専用の処理情報で、精選方法(ウォッシュド/ナチュラル等)とは別軸。他店舗でもデカフェ豆の取り扱いは十分あり得るため、Denim bis(カフェインレスカテゴリあり)・PHILOCOFFEA(ディカフェ処理欄あり)双方で確認済み |
| flavor_notes | テイスティングノートの原文。店舗によって見出しが「味わい」「風味」「フレーバー」「テイスティングノート」等に分かれる(技術的には細かい定義の違いがあるが、店舗の実務ではほぼ同義語として使われる)。フリーテキストとして保持し、正規化はSCAフレーバーホイールの9大カテゴリ(Fruity/Floral/Sweet/Nutty-Cocoa/Spices/Roasted/Green-Vegetative/Sour-Fermented/Other)を参考に将来検討する |

### PRODUCER_LOT(生産者ロット)

**新設の理由**: スペシャルティコーヒーは「生産地・生産者・農園名」を明記する慣習が強く(実際にMiLL Coffeeの詳細ページで生産者・生産地・標高・品種が構造化されて取得できた)、これは商品ごとの単発情報ではなく**「同じ生産者・農園から複数の店舗・複数のロット(精選方法違い等)が販売されうる」という、産地マスタとは別次元の実体**として扱うべきと判断した。`PRODUCT`に直接カラムを生やすのではなく、独立テーブルとして切り出している。

| カラム | 説明 |
|---|---|
| producer_name | 生産者名(例:「Kebir Coffee Trading社」) |
| farm_name | 農園名。生産者と別に農園名が判明する場合のみ(例:Denim bisの「ゴールデンビートル農園」「コルブラン農園」) |
| origin_region_id | 産地マスタ(`ORIGIN_REGION`)との紐付け。国・中分類地域レベルの正規化はここで行う |
| region_detail | 生産地の原文(例:「ベンチマジ、ゲシャ村」)。産地マスタの粒度(イルガチェフェ等の代表地域)より細かい、村・地区レベルの情報のため、無理に正規化せず原文を保持 |
| altitude_min_m / altitude_max_m | 標高(m)。「1,730-1,890m」のような範囲表記を最小・最大に分けて保持 |
| variety | 品種(例:ゲイシャ、ティピカ、パカマラ)。今回の調査では未整理だった軸だが、実データで「品種【ゲイシャ】」のように明示されるケースが確認できたため追加 |
| source_note | 抽出元の説明文原文。パース精度の検証・再パース用に保持 |

**運用イメージ**: 商品名・説明文から生産者名や農園名が抽出できた場合のみ`PRODUCER_LOT`レコードを作成・紐付け、取れない場合(Denim bisの「ドビ」「スカイヒル」のような断片的な固有名詞のみのケース)は`PRODUCT.raw_name`に残したまま無理に構造化しない。将来的に同一生産者の別ロットを横断検索する機能(例:「このケビル・コーヒー・トレーディング社の豆を扱う他の店舗」)に発展させられる設計。


### ORIGIN_COUNTRY / ORIGIN_REGION(産地マスタ)
`coffee-origin-master-draft.md`の階層(国→地域→代表銘柄)をテーブル化。

- `ORIGIN_REGION`は自己参照的に中分類・小分類を表現できるよう`parent_region`を持たせる案(またはregionテーブル自体を再帰構造にする設計も検討可)
- 例: ジャマイカ(国) → ブルーマウンテン山系(中分類) → (特定銘柄側で管理)

### DESIGNATED_BRAND(特定銘柄マスタ)
`coffee-designated-brands.md`の14銘柄をそのままマスタ化。

- `exclusion_rule`に「ブコバ地区産を除く」のような除外条件をテキストで保持。ロジック側でこの条件を評価する
- `min_blend_ratio`はブレンド表示時の最低含有率(30%)。将来的にブレンド商品の産地内訳を持たせる場合の検証に使える

### PROCESSING_METHOD(精選方法マスタ)
`coffee-processing-and-grades.md`の5系統(ウォッシュド/ナチュラル/ハニー/ウェットハルド/アナエロビック)を初期データとして投入。

### COUNTRY_GRADE(国別グレードマスタ)
**国とグレード記号のペアで1レコード**にするのが最重要ポイント。「G1」だけを保存すると国が分からず意味を失う、という調査時の教訓を反映。

| country_id | code | criteria_type |
|---|---|---|
| エチオピア | G1 | 欠点数(0〜3個) |
| インドネシア | G1 | 欠点数(0〜11個、エチオピアと基準が異なる) |
| ケニア | AA | スクリーンサイズ |
| グアテマラ | SHB | 標高 |

### ROAST_LEVEL(焙煎度マスタ)
日本式8段階を初期データとして投入。`agtron_min`/`agtron_max`は目安値として保持(店舗ごとに基準がずれる可能性があるため、あくまで参考値扱い)。

### CERTIFICATION_TAG / 中間テーブル
オーガニック・フェアトレード・COE等。商品は複数の認証を同時に持ちうるため多対多。

### POST_PROCESSING_TAG(後処理タグ)
精選方法(ウォッシュド/ナチュラル等)とは別軸の、**豆になった後の追加加工**を扱うマスタ。4店舗目の検証で「ウイスキー樽熟成コーヒー バレル エイジド」のように、精選方法ではなく後処理を商品名の主軸にする例が見つかったため新設。CERTIFICATION_TAGと同様、商品は複数の後処理タグを持ちうるため多対多。初期データ例: バレルエイジド(樽熟成)、ディカフェ(処理方法自体は別途PROCESSING_METHODで扱うが、追加加工的な性質を持つ場合はここにも重複して立てうる)

### PARSE_LOG(解析ログ)
商品名パースの結果、どの程度自動分類できたかを記録する運用テーブル。

- `confidence_score`: マスタとのマッチ度合い
- `unmatched_keywords`: マッチしなかった語句を蓄積 → 後でマスタ拡充の材料にする

## 3. 商品名パースの処理フロー(案)

1. `raw_name`を取得。あわせて店舗のカテゴリ・タグ情報があれば`category_hint`として保持
2. ブレンド/ストレートを判定(「ブレンド」「オリジナル」等のキーワード、または産地キーワードの複数検出で推定)
3. ストレートの場合、産地判定を以下の優先順位で試行し、成功した段階で`origin_source`を記録して打ち切る
   1. 特定銘柄マスタとの一致(`origin_source=brand`)。除外条件(exclusion_rule)に抵触しないか確認
   2. 国名の直接表記(`origin_source=country_name`)
   3. 地域名からの逆引き(`origin_source=region_name`。産地マスタの「代表地域」情報を検索キーとして活用。国名の記載がなくても「シダモ」等の地域名だけで判定できるケースに対応)
   4. いずれにも一致しない場合、`category_hint`(店舗のカテゴリ・タグ情報)を使って産地を補完(`origin_source=category_hint`)
4. 精選方法・焙煎度・グレードのキーワードを個別に抽出(産地判定とは独立して実行可能)。日英エイリアス辞書を使い大文字小文字を無視してマッチさせる
5. 後処理タグ(バレルエイジド等)のキーワードを抽出し、`POST_PROCESSING_TAG`との中間テーブルに登録
6. どれにもマッチしない残余キーワード(農園名・精選所名・地区名・ロット名等の固有名詞)は`farm_note`に保持しつつ、`PARSE_LOG.unmatched_keywords`にも記録
7. 一定期間ごとに`unmatched_keywords`を人力でレビューし、マスタに追記

## 5. 実データ検証結果(Denim bis 21商品)

実際の商品名でパースロジックをテストした結果、以下が判明した。

| 項目 | 判定率 |
|---|---|
| 産地(国)判定(ストレートのみ) | 16/16(100%) |
| 特定銘柄マッチ | 3/21(14%) |
| 精選方法マッチ | 4/21(19%) |
| グレード表記マッチ | 7/21(33%) |
| 焙煎度マッチ | 3/21(14%、いずれもブレンドの推奨焙煎欄) |

- 産地(国)は店舗の命名規則(先頭に国名を置く)に助けられ高精度。ただし店舗ごとの命名規則への依存度が高い点は今後複数店舗で検証が必要
- 特定銘柄マッチングは「コロンビア エメラルドマウンテン」(公正取引協議会の14種には含まれない店舗独自ブランド名)を誤って特定銘柄と判定しなかった。**法的な特定銘柄と店舗独自の商業ブランド名を混同しない**という意味では正しい挙動
- 焙煎度マッチ率が低かった理由は精度の問題ではなく、**Denim bisが「注文時に焙煎度を選ぶ」販売方式のため、単一原産地の商品名にそもそも焙煎度が含まれていない**ことが判明。店舗によって「商品名に焙煎度が固定で書かれている」パターンと「注文時選択」パターンが混在すると想定される
- 未マッチの残余キーワードとして、農園名・精選所名・地区名・ロット名(例:「ドビ」「ゲデブ」「スカイヒル」「ゴールデンビートル」「コルブラン農園」「ビンタン・リマ」)が多数見つかった。これらは産地マスタにも特定銘柄マスタにも存在しない情報のため、`farm_note`という自由記述カラムで別途保持する方針とした

## 7. 2店舗目(珈琲問屋)での追加検証

同じパーサーを珈琲問屋の実商品名9件に適用したところ、産地判定率が100%→67%に低下した。原因は3パターン:

1. **国名の表記ゆれ**: 「ガテマラSHB」のように、Denim bisの「グァテマラ」表記に対し珈琲問屋は「ガテマラ」(ァ抜き)を使用。同じ国でも店舗ごとに表記が異なる
2. **業界慣用銘柄名の欠落**: 「モカシダモG4」の「モカシダモ」は国名を含まず、かつ公正取引協議会の14特定銘柄にも含まれていない(正式に定義されているのは「モカ・ハラー」のみ)。**「法的な特定銘柄」でも「産地の直接表記」でもない、業界の慣用的な通称**という第3のカテゴリが存在することが判明
3. **産地マスタの収録漏れ**: 「ドミニカ ハラバコア」のドミニカ共和国が未収録

### 反映方針

- `ORIGIN_COUNTRY`マスタに表記ゆれを許容する`alias`(エイリアス)を持たせる設計に変更(例: グアテマラ = {グァテマラ, グアテマラ, ガテマラ})
- 「モカシダモ」「モカイルガチェフェ」等の**業界慣用銘柄名テーブル**(`TRADE_NAME`のような名称)を新設し、法的な`DESIGNATED_BRAND`(14種)とは別に管理。慣用銘柄名は産地(国)への紐付けだけを持たせるシンプルな構成でよい
- 産地マスタの国リストは今後も店舗を増やすたびに漏れが見つかる前提で、`PARSE_LOG.unmatched_keywords`から定期的にレビューする運用を前提にする

## 9. 産地判定ロジックの改善: 地域名からの逆引き

珈琲問屋の「モカシダモG4」が産地判定に失敗した原因を分析したところ、**「モカシダモ」に国名(エチオピア)の文字が一切含まれていない**ことが判明。ただし「シダモ」はエチオピアの地域名であり、コーヒーに詳しい人には国名がなくても伝わる、という店舗側の前提があると考えられる。

これを受け、産地判定ロジックに**地域名からの逆引きステップ**を追加した。

```
産地判定の優先順位:
1. 特定銘柄(14種)からの逆引き(国が一意に確定)
2. 国名の直接表記
3. 地域名からの逆引き(産地マスタの「代表地域」情報を国への逆引き辞書として活用)
```

この改善により、珈琲問屋の産地判定率は67%→**100%**まで向上した。産地マスタ(`coffee-origin-master-draft.md`)の「国→代表地域」の階層情報は、当初は分類の整理目的で作成したものだったが、**そのままパースの検索キーとして機能する**ことが実証された。`ORIGIN_REGION`テーブルは地域名から国を逆引きできるインデックスとしても活用する設計とする。

## 11. 3店舗目(英語表記)での追加検証

豆男珈琲(base.shop)は「Ethiopia Sidamo Bona Zuria Sedaka Natural」のように**英語表記を主体とした商品名**を使う店舗。国名・精選方法の英語キーワードを追加し、大文字小文字を無視するマッチングにしたところ、産地判定率100%を達成した。

| 項目 | Denim bis(日) | 珈琲問屋(日) | 豆男珈琲(英) |
|---|---|---|---|
| 産地(国)判定率 | 100% | 100% | 100% |
| 精選方法マッチ | 19% | 11% | 71%(英語店の方が高精度) |
| グレード表記マッチ | 33% | 67% | 14% |

### 分かったこと

- **国名・精選方法(Washed/Natural等)は固定語彙で種類が少ないため、日英対応表を追加するだけで低コストに対応できる**
- 精選方法は英語表記の店の方がむしろ高精度だった。「Natural」「Washed」を明記する文化的傾向があり、日本語の「ナチュラル」「ウォッシュド」より省略されにくい
- 一方、農園名・地区名(Kianyangi、Guji Ana Sora等)は**無限に増える固有名詞**であり、マスタ化ではなく`farm_note`の自由記述で保持する方針を維持する(既存の結論と一致)
- グレード・特定銘柄のマッチ率が店によって大きく異なるのは、パーサーの精度問題ではなく**店舗ごとの命名スタイルの違い**(グレード記号を書く店/農園名主体で書く店)によるもの

### 設計への反映

`ORIGIN_COUNTRY`・`PROCESSING_METHOD`等の固定語彙マスタは、**日本語表記と英語表記を1つの正規化値に紐付ける多対1のエイリアス構造**を前提にする(先述の「表記ゆれ」対応と同じ仕組みで、言語違いも吸収できる)。

## 13. 4店舗目(MiLL Coffee)での追加検証

MiLL Coffee(Wixベース)の実商品19件で検証したところ、産地判定率が初めて100%を下回り**89%**(17/19)となった。

### 未判定2件の分析

- 「ノースサンタンテール シルキーゴールド」: 国名・地域名・特定銘柄名のいずれも商品名に含まれない
- 「ウイスキー樽熟成コーヒー バレル エイジド」: そもそも**産地ではなく「後処理・熟成」を商品名の主軸にしている**。精選方法(ウォッシュド/ナチュラル等)とも異なる、**第7の軸(バレルエイジ等の後処理)**の存在を示唆する

### 「ブルーマウンテン№1」の成功例

商品名に「ジャマイカ」の文字がなくても、**特定銘柄マスタからの逆引きで正しく国を確定できた**。特定銘柄名だけで販売される商品が実在することを裏付ける結果。

### 設計への反映

4店舗を通じて、産地判定に失敗するのは一貫して「農園名・特殊processing名のみで構成され、国名/地域名/特定銘柄名のいずれも含まない商品名」のケースだった。これへの対応として:

- **商品名だけに頼らず、店舗のカテゴリ・タグ情報(例: MiLL Coffeeの「原産国」フィルタ:エチオピア/ブラジル/コスタリカ...)を産地推定の補完情報として取得する**方針を追加する。`PRODUCT`テーブルに`category_hint`(スクレイピング時に取得したカテゴリ・タグの原文)を持たせ、商品名パースで産地不明の場合のフォールバックとして使う
- それでも判定できない場合は`PARSE_LOG`に残し人力で補完する運用を維持
- 「バレルエイジド」のような後処理情報は、`PROCESSING_METHOD`(精選方法)とは別に`POST_PROCESSING_TAG`(樽熟成等)を持たせる案を今後検討

## 15. フレーバーコーヒーの分離・除外方針

焙煎時・焙煎後に人工的な香り付け(バニラ、ヘーゼルナッツ、キャラメル等)をしたコーヒーは、近年市場で増えている一方、**産地・精選方法・グレードといった豆本来の個性を扱う本アプリの趣旨とは根本的に異なる商品カテゴリ**であるため、完全に分離・除外する方針とした。

- 実データ検証(珈琲問屋)で「フレーバーコーヒー ココナッツ」「フレーバーコーヒー アーモンド」という実例を確認済み
- パースロジック上、**フレーバーコーヒーの判定を他のどの分類よりも優先**して行う。該当する場合は`category = "フレーバー"`、`is_flavored = true`を設定し、産地・精選方法・グレード等の解析処理自体をスキップする(ベース豆の産地表記があっても、商品の主眼は香り付けでありノイズになるため)
- スクレイパー(`build_product_records`/`scrape_all_products`)は**通常商品(products)とフレーバーコーヒー(flavored_products_excluded)を出力段階で完全に分離**する。データとしては保持しつつ(サイレントに欠落させない)、アプリの通常商品一覧には一切表示しない設計とした
- フレーバー名(ココナッツ、アーモンド等)自体は`flavor_name`として参考情報を保持するが、判定ロジックには使わない(あくまで「フレーバーコーヒー」という明示的な表記の有無で判定する)

## 17. 複数実店舗への対応(SHOP_LOCATIONの新設)

PHILOCOFFEA(World Brewers Cup優勝者が経営)を調査する過程で、**オンラインストアに加えて複数の実店舗**(シャポー船橋店、プラッツ習志野店、201、表参道店、焙煎所)を持つことが判明。加えて、店舗ページには「本社機能で来店対象ではない」拠点(ROASTERY)も混在していた。

これまでの`SHOP`テーブルは「1店舗=1住所」を前提にしていたため、この構造には対応できなかった。`SHOP_LOCATION`を新設し、`SHOP`から1対多で参照する形に変更した(詳細は上記`SHOP_LOCATION`項を参照)。`is_headquarters`フラグにより、消費者向けの店舗一覧には出したくない拠点(本社・焙煎所)を除外できる設計にしている。

この変更により、以下3パターンすべてに対応できる:
- オンライン専業(`shop_type=online_only`、`SHOP_LOCATION`レコードなし)
- 実店舗1件(`shop_type=single_location`、`SHOP_LOCATION`レコード1件)
- 実店舗複数(`shop_type=multi_location`、`SHOP_LOCATION`レコード複数件、店舗詳細画面で一覧表示)

## 19. 大会・イベント情報の収集(EVENT_SOURCE / EVENTの新設)

商品・店舗と同じ「スクレイピングして自動更新する」設計思想を、大会・イベント情報にも適用する。目的は、豆知識タブで学んだ団体(SCA/ACE/CQI/SCAJ等)の活動を、実際に開催される大会・展示会・オークションという「動いている情報」として提示すること。産地(Cup of Excellenceの対象国)や特定銘柄との相互リンクも視野に入れる。

### EVENT_SOURCE(収集元団体)

商品スクレイパーの`SHOP`に相当する、イベント情報の収集元。1団体が複数のイベント一覧ページを持つ場合は、まず主要な公式カレンダー/ニュースページ1つに絞って着手する。

| カラム | 説明 |
|---|---|
| update_cadence | 商品在庫と違い、大会日程は日次で変わるものではないため月次更新を想定。運用コスト(courtesy delay等)を抑えられる |
| robots_txt_status | 商品スクレイパーと同様、着手前に必ず確認する |

### EVENT(個別の大会・イベント)

| カラム | 説明 |
|---|---|
| event_type | competition(競技会。World Barista Championship等)/exhibition(展示会。SCAJ展示会等)/auction(オークション。Cup of Excellenceのオンラインオークション等)/conference(カンファレンス) |
| related_country_id | Cup of Excellenceのように「その国のコーヒー」を対象とした大会の場合、`ORIGIN_COUNTRY`と紐付け、産地タブとの相互リンクを可能にする |
| related_brand_id | 特定銘柄に関連するイベントがあれば紐付け(現時点では想定用途は限定的) |

### 候補ソースの初期リスト(2026年8月時点で存在を確認済み)

| 団体 | 想定ページ | 備考 |
|---|---|---|
| SCA | calendar.sca.coffee(Localist系カレンダー) | World Coffee Championships(旧WCE)の各種大会・World of Coffee展示会等を含む可能性 |
| ACE / Cup of Excellence | cupofexcellence.org | 国別開催スケジュール・オークション日程 |
| SCAJ | scaj.org | SCAJ展示会・ジャパンバリスタチャンピオンシップ等 |

**次の実装ステップ**: 商品スクレイパーと同じ手順で、①各サイトのrobots.txt確認 → ②実際のカレンダーページのHTML構造確認 → ③パーサー実装、という順に進める。イベント一覧ページは商品一覧よりシンプルな構造(日付・タイトル・場所の羅列)であることが多く、比較的着手しやすい見込み。

## 20. 今後の検討事項

- **`ORIGIN_REGION`の階層設計**: 現状「中分類・小分類」を1つのテーブルに`parent_region`で表現する案にしているが、正式には再帰的な自己参照テーブル(`parent_region_id`で自テーブルを参照)にした方が将来的な拡張(小分類のさらに下の階層等)に強い
- **未調査の分類軸**: 品種(ティピカ/ブルボン/カトゥーラ等)、認証(オーガニック/フェアトレード/COE)の詳細は今回のマスタに含めていない。必要であれば別途調査してテーブルを追加
- **価格比較機能**: 同一`designated_brand_id`または`origin_region_id`を持つ商品を横断検索すれば実現できる設計になっている
- **地図機能**: 別途検討した通り、Googleマップは自前DB化せず店舗詳細から外部リンクで開く方針のため、`SHOP`テーブルに緯度経度を持たせる程度で十分
