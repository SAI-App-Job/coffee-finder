# 調査・記事作成・提示のルール

アプリに載せる情報(産地ガイド、豆知識、用語集、淹れ方、競技会など)は、このルールに従って調べ、書き、検証し、ユーザーへ示す。
**出典を台帳に記録できない記述は、アプリに表示してはいけない。**(例外なし)

制定: 2026-11-08。背景は `docs/source-audit-2026-11.md`(出典のない記述が多く、全項目の再調査が必要になった経緯)。

## 1. 役割は分ける

| 役割 | 責任 |
|---|---|
| 調査 | 情報源を探し、**原文を読み**、台帳に記録する |
| 執筆 | 台帳に載った事実だけで文を書く。根拠より強く書かない |
| 検証 | 書かれた文を、台帳と1文ずつ突き合わせる。**執筆者とは別の担当**(サブエージェント)が、原文を取り直して確かめる |
| 提示 | ユーザーへの報告・画面表示・ストア掲載文で、確認した範囲を偽らない |

## 2. 情報源の優先順位

1. 各国政府、各国のコーヒー機関・規格機関・協会の**公式サイトと公式文書**(規則、規格、報告書の原文)
2. 国際機関・国際団体の公式文書(ICO、SCA、WCR、WCE、USDA FASなど)
3. 報道・業界紙・小売店・Wikipedia・ブログ: **補助にとどめ、採用の根拠にしない**

- 公式と食い違うときは、**独立した複数の根拠**を徹底的に探す。報道1本で決めない。
- 食い違う情報源を採用するときは、**採用前にユーザーの確認を取る**。
- **孫引き禁止**。要約・報道・検索結果に書かれた引用を根拠にしない。引用元の一次資料まで遡り、本文を開いて確認する。

## 3. 「読んだ方法」(readMethod)

台帳に残す資料は、必ず次のどれで読んだかを区別する。

| readMethod | 意味 | 台帳の根拠にできるか |
|---|---|---|
| `full-text` | 原文(ページ全体、PDF全文)を取得し、**該当箇所を実際に読んだ** | できる |
| `excerpt` | 一部だけ読んだ(ページが切れた、要旨のみ) | できない(読んだ範囲に書いてある事実に限り、個別に`full-text`扱いの根拠にしてよい) |
| `snippet` | 検索結果の要約・断片だけ | できない。手がかりにすぎない |
| `failed` | 取得できなかった(403、接続エラーなど) | できない。失敗として記録し、別の資料で代用して済ませない |

- ページ取得ツールは、小さなモデルが要約して返す。**要約は引用ではない。** `quote` には、取得した生の本文からそのままの文を写す。PDFは `pypdf` で本文を抽出して読む。生のHTMLは `curl` で取得して確かめる。
- 取得ツールの読みや数字(人名のローマ字表記など)は、不安定なことがある。原文で確かめる。

## 4. 台帳の様式

台帳は2つのJSON。`src/data/ledger/sources.json`(資料の一覧)と `src/data/ledger/entries.json`(記述ごとの根拠)。
検証の途中成果は、`docs/ledger-drafts/<範囲>.json` に同じ形式で書く(アプリは読まない)。

### 資料(sources)

```json
"fnc-circular-007-2025": {
  "title": "Circular N° 007 - Regulación cafetera (2025-12-17)",
  "org": "Federación Nacional de Cafeteros de Colombia",
  "url": "https://...",
  "kind": "primary",
  "readMethod": "full-text",
  "accessed": "2026-11-08"
}
```

- `kind`: `primary`(政府・機関・協会の公式文書)/ `secondary`(報道・業界紙など)
- `id` は `<機関>-<短い名前>`。同じ資料は同じ`id`を使う。

### 記述(entries)

キーは `種類:名前[:項目]`。

| 種類 | キー | 範囲 |
|---|---|---|
| 豆知識 | `fact:<title>` | 1話 |
| 用語集 | `glossary:<term>` | 1用語(summary+detail) |
| 淹れ方 | `brew:<method>` / `extraction:<key>` / `diagnosis:<label>` | 1件 |
| 産地ガイド | `origin:<country>:<field>` | field = tagline / regions / terroir / harvestSeason / varietiesDetail / farmStructure / history / gradeSystem / officialBody |
| 産地のサブ産地 | `origin:<country>:sub:<name>` | 1サブ産地 |
| 品種 | `variety:<lineage>` | 1系統 |
| 特定銘柄 | `brand:<name>` | 1銘柄(名称+注記+解説) |
| 精選方法の解説 | `processing:<name>` | 1件 |
| グレードの解説 | `grade:<kind>` | `src/utils/grade.js` の分岐ごと |
| 競技会 | `competition:<id>:<field>` | field = tagline / history / format / latestResult |
| 大会・イベント | `event:<name>` | 1件 |
| フレーバーホイール | `flavorwheel:all` | 全体 |

```json
"origin:コロンビア:officialBody": {
  "status": "verified",
  "claims": [
    {
      "text": "FNCは1927年設立",
      "status": "verified",
      "sourceIds": ["fnc-..."],
      "quote": "原文のそのままの文(200字以内)",
      "location": "条項・ページ・見出し"
    }
  ],
  "suggestedText": "未確認の主張を除いた日本語の本文(直す必要があるときだけ)",
  "note": ""
}
```

- 本文を**事実1つごとの主張(claims)に分けて**検証する。
- 主張の `status`: `verified`(根拠の原文と一致)/ `unverified`(根拠が取れない)/ `incorrect`(原文と食い違う)/ `conflict`(資料どうしが食い違う)
- 記述の `status` は、全主張が`verified`のときだけ `verified`。
- **表示してよい条件**(アプリの検査): 記述が`verified`で、全主張に`primary`かつ`full-text`の資料が1つ以上ある。二次資料だけの主張は、ユーザーの承認(`approvedSecondary: true`)がなければ表示しない。
- `textHash`: 検証した本文のハッシュ。本文を変えると検査が失敗し、再検証が必要になる。

## 5. 書き方

- 台帳にない主張は書かない。書く強さは根拠に合わせる(「〜と発表した」「〜年時点」「〜とされる」を使い分ける)。
- 推論を事実として書かない(例: 続柄が未確認なのに「娘」と書く)。
- 数字は単位と年を添える。「最新」「現在」は確認日を添える。
- 翻訳は、日本語の本文と同じ主張だけを訳す。主張を足さない。
- 出典は画面に出す(資料名・リンク・確認日)。内部メモ(`docs/` のパス)は出典にならない。

## 6. 報告のしかた

- 報告には、確認した範囲、確認できなかった範囲、確認方法(`full-text` か否か)を書く。
- 「徹底」「全項目」は、実際にそうなったときだけ使う。
- 自分の誤りは、見つけた時点で最初に伝える。
- ストア掲載文など、ユーザー向けの文章にも同じ基準を適用する(数字はデータの件数で裏付ける)。

## 7. 再確認の期限

規格、機関名、最新結果は古くなりやすい。台帳の`accessed`から**12か月**を過ぎた資料は、再確認の対象にする。
