# スクレイパー実装ログ(不具合パターン集)

新しい店舗のスクレイパーを実装するたびに、実データ検証(実際のワークフロー実行・
ブラウザ確認)で見つかった不具合とその対処をここに追記する。目的は同じ種類の
不具合を将来の店舗実装で繰り返さないこと。バグが無く素直に実装できた店舗は
記載しない(記載するのは「発見した不具合」があるケースのみ)。

フォーマット:

```
## [店舗名]（プラットフォーム、実装日）
- 発見した不具合: ...
- 対処: ...
- 影響した既存データ: ...(あれば)
```

実在確認したが実装を見送った店舗(オンラインショップが無い、閉店済み等)は
このファイルではなく`docs/not-implementable-shops.md`に記録する。

---

## コーヒーランド（独自HTML、2026-09-04）
- 発見した不具合: 商品一覧を正規表現で直接パースする実装にしたところ、GitHub
  Actionsから実行すると0件しか取得できなかった。サーバーがContent-Type
  ヘッダーにcharsetを付けずUTF-8のHTMLを返しており(`file`コマンドで実体は
  UTF-8と確認済み)、requestsライブラリがcharset未指定時にデフォルトの
  ISO-8859-1で`resp.text`をデコードしてしまい、正規表現が(理論上はASCII
  部分のタグ構造だけで完結するはずだが)実際にはマッチしなくなっていた。
- 対処: `resp.encoding = "utf-8"`を明示的に指定してから`resp.text`を
  読むように修正。デバッグ出力(`html_len`/`matches`件数)で修正後40件
  正しく取得できることを確認済み。
- 影響した既存データ: 初回実装時点でまだ収録前だったため既存データへの
  影響は無し。charsetヘッダーが欠落した静的サイトを今後実装する際は要注意。

## Peppino Coffee Roaster・FIVE COFFEE STAND&ROASTERY（WooCommerce/BASE、2026-09-04）
- 発見した不具合: `BeautifulSoup(text, "xml")`でsitemap.xmlを解析する実装にしたところ、
  GitHub ActionsのCI環境には`lxml`パッケージがインストールされておらず
  `bs4.exceptions.FeatureNotFound`で例外終了した(ローカルの動作確認では発生しない、
  CI環境固有の依存関係不足)。
- 対処: プロジェクトの他の全スクレイパーと同じく`"html.parser"`(標準ライブラリのみで
  動作)に統一した。XML文書をhtml.parserで解析すると警告が出るが動作に支障はない。
- 影響した既存データ: 初回実装時点でまだ収録前だったため既存データへの影響は無し。

## FIVE COFFEE STAND&ROASTERY・入谷珈琲豆店（BASE、2026-09-04）
- 発見した不具合: 両店とも商品詳細ページの`window.dataLayer.push({...})`という
  Googleタグマネージャー向けJSオブジェクトから`item_name`/`itemPrice`を正規表現で
  抽出する実装で作ったところ、実際にGitHub Actionsから実行すると0件しか取得できな
  かった。デバッグ出力で調査したところ、GitHub Actions環境からのリクエストに対して
  返るHTMLには`dataLayer`のスクリプト自体が含まれていなかった(手元の開発環境からの
  リクエストでは含まれていた)。ボット検知等によりGTM/アナリティクス関連スクリプトが
  条件付きで除去されている可能性が高い。
- 対処: 常に静的に出力されるSNSシェア用OGP(Open Graph)メタタグ
  (`meta[property="og:title"]`・`meta[property="product:price:amount"]`)から
  商品名・価格を取得する方式に変更した。OGPはFacebook/Twitter等の外部クローラーが
  読める必要があるため、ボット向けに除去されにくいと考えられる。同じくBASEの
  `application/ld+json`のProduct構造化データを使う他の実装(BEANS珈琲・ROOT COFFEE等)
  は今回のCI実行で問題無く動作しており、影響はGTMのdataLayerに全面的に依存していた
  この2店舗のテーマ限定と見られる。
- 影響した既存データ: 初回実装時点でまだ収録前だったため既存データへの影響は無し。
  同様のdataLayer依存のテーマを使うBASE店舗を今後実装する際は要注意。

## ライブコーヒー（おちゃのこネット(Ocnk)、2026-09-03）
- 発見した不具合: 同じOcnkクリーンURL方式(/product-list/N)の店舗でも、
  テーマのバージョンが店舗ごとに異なっていた(米本珈琲は"touch001"、
  ライブコーヒーは"touch035")。米本珈琲用に確認したDOM構造
  (`a.item_data_link`)をそのままライブコーヒーにも流用してしまい、
  実際のクラス名は`a.list_item_link`だったため一覧ページの商品が0件で
  返っていた。ローカルでのcurl事前確認では「li.list_item_cellの件数」しか
  見ておらず、内部のリンク要素クラス名まで個別に確認していなかったことが
  根本原因。
- 対処: 実ワークフロー実行時にHTMLを一時的にデバッグ出力(GitHub Actions側の
  実際のレスポンスをその場で確認)し、`a.list_item_link`が正しいクラス名だと
  特定。セレクタを修正し、デバッグコードは元に戻した。
- 影響した既存データ: なし(初回実装時に発見。0件のまま気づかず放置していれば
  店舗自体が実質的に空データとして扱われるところだった)。
- 教訓: 「同じプラットフォーム・同じURL方式」であっても、店舗ごとにテーマ
  バージョンが異なりDOM構造が食い違うことがある。一覧ページのDOM確認は
  必ず対象の店舗自身のHTMLで個別に行い、他店舗の確認結果を流用しない。

## 十一房珈琲店（手動データ登録、2026-09-04）
- 発見した不具合: 手動データのproductUrlを、同じ豆の焙煎度違い2商品
  (例:「ペルー・アンデスブルー」のフルシティロースト版とフレンチロースト版)

- 発見した不具合: 商品タブの「近い順」ソート機能を実装する際に確認したところ、
  499店舗中たった3店舗しかlat/lngを持っていなかった。原因は2つの独立した
  不具合の組み合わせ:
  1. `scripts/geocode-shops.js`が`shop.locations`(複数拠点店舗)しか
     ジオコーディング対象にしておらず、単一拠点店舗(全店舗の大半)は
     一度もジオコーディングされていなかった。
  2. `aggregate_shops.py`の`merge_shop()`が、単一拠点店舗のトップレベル
     lat/lngをそもそも出力フィールドに含めていなかった(複数拠点店舗も
     `locations[].lat/lng`は`merge_locations()`で引き継ぐが、トップレベル
     の代表座標ミラーは出力していなかった)。このため仮に(1)を先に直しても、
     毎週のスクレイピング再集約のたびに`data/shops.json`が丸ごと再構築され、
     ジオコーディング結果が失われてしまう構造だった。
  1つ目の不具合だけが目立つ形で表面化していた(「ジオコーディングされて
  いない」ように見えた)が、根本原因は2つ目(集約処理がlat/lngを引き継がない)
  であり、1つ目を直すだけでは再集約1回で振り出しに戻っていた。
- 対処:
  - `merge_shop()`に、単一拠点店舗はexisting_shopのトップレベルlat/lngを
    引き継ぐ処理、複数拠点店舗はlocations[0]の座標をトップレベルにも
    ミラーする処理を追加。
  - `geocode-shops.js`を拡張し、単一拠点店舗のトップレベルlat/lng・
    `scraper/manual/shops/*.json`の手動店舗も対象に含めた。
  - 拡張版で再実行し、472/499店舗(94.6%)まで復旧。残り27店舗は「字」を
    含む農村部の大字・小字名や番地レベルの住所がNominatim(OpenStreetMap)
    で解決できなかった店舗。
  - 追加対処: `addressCandidates()`に市区町村レベルまで切り詰める
    フォールバック候補(例:「愛知県安城市小川町的場101-7」→「愛知県安城市」)

    唯一住所自体が未確認だった手動入力店舗(It's roasted coffee、
    Instagram/Googleマップのみで公式サイト無し)は、Instagram公式アカウント
    自身のプロフィール欄(一次情報)から住所を確認・追記した上でジオ
    コーディングし、最終的に499/499店舗(100%)の座標を確保した。
- 教訓: 「一括バッチスクリプトが書き込んだ値」を、それとは別に毎回全体を
  再構築するパイプライン(aggregate_shops.py)が上書き・消去してしまう
  構造は見落としやすい。同種のフィールドを新設する際は、(a)バッチ
  スクリプト単体でのテストだけでなく、(b)その後にメインの集約処理を
  1回走らせてもフィールドが生き残るかまで確認する。
- 影響した既存データ: 実質全店舗(496/499)が対象。既存データの誤りでは

## 優先順位③(総点検)着手: decaf_processの一括推定(2026-09-19)

- 経緯: 世田谷区で見つかった③④の基準を全店舗(約380〜499店舗)に広げる前に

- 追記バグ修正: 上記の一括推定をdata/products.jsonへの直接パッチ(移行スクリプト)
