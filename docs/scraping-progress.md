# スクレイパー実装ログ(不具合パターン集)

新しい店舗のスクレイパーを実装するたびに、実データ検証(実際のワークフロー実行・
ブラウザ確認)で見つかった不具合とその対処をここに追記する。目的は同じ種類の
不具合を将来の店舗実装で繰り返さないこと。バグが無く素直に実装できた店舗は
記載しない(記載するのは「発見した不具合」があるケースのみ)。

フォーマット:

```
## [店舗名]（プラットフォーム、実装日）
- 発見した不具合: ...
- 対処: ...
- 影響した既存データ: ...(あれば)
```

---

## HIMONYA FIVE COFFEE（BASE、2026-09-03）
- 発見した不具合: (1)商品名末尾に「(生豆Ng)」という生豆(焙煎前)重量の表記が
  付いているが、この店は注文後焙煎モデルで、実際の販売重量は焙煎後の目減りした
  値(説明文に「生豆240gを焙煎し、焙煎後は約200gとなる」等の明記あり)。生豆重量を
  そのままweight_gに使うと実際に届く量と食い違う。(2)ブレンド判定をタイトルの
  「ブレンド」の語に頼れない。単一原産地商品の多くはタイトルに国名すら無く、
  逆に9件中2件のブレンドしかタイトルに「ブレンド」を含まない。
- 対処: (1)説明文の「焙煎後は約Ng」という明記を正規表現(WEIGHT_ROASTED_PATTERN)で
  抽出し、生豆重量ではなくこちらをweight_gに採用。(2)構造化された「原産国」欄が
  「（ブレンド）」を含むかどうかでブレンド判定する方式に変更(タイトル文字列に
  頼らない)。
- 影響した既存データ: なし(新規実装時に発見)

## びーんず亭（EC-CUBE、2026-09-03）
- 発見した不具合: 商品説明文の標高情報が、本来の標高ラベルではなく「生産地区」
  ラベルの値としてそのまま入っている実例が1件あった(店舗側の入力ミスと思われる)。
  特定のラベルキーだけを信頼すると、この商品だけ標高が欠落する。
- 対処: 特定のラベルキーに依存せず、商品詳細のヘッダーブロック全体のテキストを
  「標高」パターンで正規表現検索する方式に変更。「生産地区」ラベルの値が標高の
  ような文字列に見える場合はそちらへのフォールバックをスキップする。
- 影響した既存データ: なし(新規実装時に発見)

## たまじ珈琲（WordPress + USC-e-Shop、2026-09-03）
- 発見した不具合: 「たまじブレンドJOKER」が2つの原産国(「ジャマイカ、ブラジル」)を
  1つの`<p>`タグ内にカンマ区切りで記載しており、他のブレンド商品のように別々の
  `<p>`要素になっていなかった。既存のブレンド判定ロジック(`<p>`要素数を数えて
  `len(origin_values) > 1`)ではこの1個の`<p>`しか見えず「単一原産地」と誤判定。
  結果として`category="ブレンド"`(タイトルの「ブレンド」から判定)なのに
  `origin_country="ブラジル"`が入る自己矛盾レコードが生成されていた。
- 対処: 各`<p>`の値をさらにカンマ(`、`/`,`)で分割してから件数をカウントするよう
  修正。また`category`が常にこの構造的シグナル(件数)に一致するよう、双方向に
  補正するよう変更(修正前は「ブレンド」に強制するだけで、逆に単一原産地と
  判明した場合に「ストレート」へ戻す処理が無かった)。
- 影響した既存データ: たまじブレンドJOKERの1件。手動でレコードを削除し
  再スクレイピングして修正を確認。

## MARUTAKE COFFEE BEANS（BASE、`.official.ec`、2026-09-03）
- 発見した不具合: (1)**weight_gの信頼性**: 商品説明文の【内容量】欄が、重量
  バリエーション違いのページ間でコピペミスをしていた。200gの商品ページ
  (価格は200g分の¥7,400)なのに、説明文の【内容量】は100gページからそのまま
  コピーされた「100g」のままだった実例を63件中6件で確認。(2)カテゴリに
  「オンライン限定...ギフトセット...スペシャルティセット」という、特定の
  一豆を指さないアソート商品3件が紛れ込んでいた。
- 対処: (1)説明文の【内容量】より、商品名末尾の（Ng）表記(価格と整合する、より
  信頼できる一次情報)を優先するparse_weight_from_title()を追加し、説明文側は
  フォールバックに格下げ。(2)NON_BEAN_KEYWORDS = ["ギフトセット"]で除外する
  ロジックを追加。
- 影響した既存データ: MARUTAKE COFFEE BEANSの63件全レコードを一度クリアし、
  再スクレイピングで60件(ギフトセット3件除外)に修正することを確認。

- 影響した既存データ: なし(新規実装時に発見)

## 隠房（BASE、`.theshop.jp`、2026-09-03）
- 発見した不具合: **部分文字列誤爆(フルシティ/シティ衝突)**。
  `coffee_parser.py`の`ROAST_KEYWORDS`辞書が「シティ」→「フルシティ」の順に
  並んでいたため、「フルシティロースト」を含む商品名が、辞書探索順の影響で
  「シティ」との部分一致に先に引っかかり、誤って`roast_level="シティロースト"`と
  判定されていた(隠房の「季節（月替り）シティ～フルシティロースト」で顕在化)。
  この辞書は全店舗共通のモジュールにあるため、隠房固有ではなく既存の他店舗
  データにも影響していた。
- 対処: `ROAST_KEYWORDS`の判定順を「フルシティ」→「シティ」に入れ替え
  (`GRADE_PATTERN`のG-1→G1正規化コメントや`kunikuni.py`のROAST_GROUP_LABELS
  判定順と同じ「長い表記を先に判定する」原則を徹底)。
- 影響した既存データ: Mui(別プラットフォーム、無関係の既存店舗)の2件
  (「あまにがいブレンド（フルシティロースト）」等)が、修正前のロジックで
  誤って`roast_level="シティロースト"`のまま止まっていたことを
  `data/products.json`全件検索で確認。該当2件を削除し再スクレイピングで
  `roast_level="フルシティロースト"`へ修正されたことを確認。

## GONZO CAFE&BEANS（BASE、2026-09-03）
- 発見した不具合: 実店舗のユーザー指定ドメイン(`gonzo-coffee.com`)はDNS解決
  不可(実在しないドメイン)で、実際のショップは別ドメイン(`gonzocb.base.shop`)
  だった。またこのショップはカテゴリ分けが無くsitemap.xmlの全55件を手動で
  確認したが、そのうち1件「権蔵水出しアイスコーヒー（30g×10個）」は豆の
  抽出済み水出しパック(既製品)であり、豆単品ではないことを手動調査時に
  見落とし、実際のワークフロー実行後のデータ検証(実データ全件のraw_name一覧
  確認)で発覚した。
- 対処: `NON_BEAN_KEYWORDS = ["水出しアイスコーヒー"]`を追加し除外する
  ロジックを実装(MARUTAKE COFFEE BEANSのギフトセット除外と同じパターン)。
- 影響した既存データ: なし(初回実装時に発見・即修正)
